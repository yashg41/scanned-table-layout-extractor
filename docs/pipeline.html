Table line extraction — what each stage does

The pipeline in analyse(), stage by stage, with the reasoning behind each test. Stages marked changed were altered in the current round. Counts are from one scanned title block (~1900×380 working px).

0

Upload and render should change

store.py · get_pixmap(colorspace=…)

The PDF is uploaded, each page rasterised once at the chosen dpi and cached as a PNG. The user then draws a box on that render, and the box is what the pipeline below receives.

Today: colour is discarded here, before anyone has seen the document The render is colorspace=pymupdf.csGRAY, so the cached PNG is colour type 0 — a single channel. Every later stage inherits that, and no decision made downstream can get the colour back.

This is the earliest possible moment to throw information away, and the moment with the least evidence available. Nothing at upload time knows whether the document has a tinted ground, a coloured stamp, or a blue-ink signature.
Should be: keep the upload as given, decide after the crop

stored rendergreyscalecolour, as the PDF has it
user marks boxes onthe grey renderthe original page
collapse to greyat upload, fixedafter the crop, chosen
reversible?no — colour is goneyes — colour is still on disk
The pipeline itself does not change: it still reads one channel. What changes is when that channel is chosen, and that it can be chosen again without re-uploading.

Cost: roughly 3× the page cache, and the tone stages (darkenValue, applyTone, the threshold) each need to know which channel they are reading.

Crop and enlarge

enlargeFactor() · cropCanvas()

The table's bounding box is cut from the rendered page. A table under 40% of page area is magnified toward a 1000 px target width, capped at 4× — a small table is unreadable at natural size.

Why area, not width A wide thin strip and a small square can share a width while occupying very different amounts of the page.

Darken — pull content away from the background

darkenValue(d[j], g) = 255 · (d[j]/255)g

A gamma curve, g from the darken slider (default ×1.6). It is a relative move: every pixel shifts by a proportion of where it already sits, not by a fixed amount. Monotonic — no pixel ever gets lighter, black stays black, white stays white, only the midtones move down.

What this stage is really doing Together with cut it is the only place the pipeline separates content from paper. Antialiasing leaves strokes averaging well above black, so a faint rule can sit just above the cut and vanish entirely. Darkening widens the gap between ink and background before the decision is made.
Colour is destroyed on upload, not here should change store.py renders every page colorspace=pymupdf.csGRAY and caches a PNG that is colour type 0 — one greyscale channel, confirmed from the file header. So a cyan guilloche is already grey before the browser sees it, and the page looks grey because it is.

That is why this code reads d[j]. It is not a choice of "the red channel": the canvas expands one grey byte into R=G=B, so d[j] is the grey. There is no second channel to read and nothing to convert.

What should change: keep the upload as the user gave it. Render and store the page in colour, let the user draw boxes on the original, and take the crop from that. Then the greyscale decision happens after the crop, where there is evidence to base it on — and it becomes reversible, because the colour is still on disk.
And there is no single right way to collapse colour open Which is the real argument for deciding late. Measured across the ink types these documents actually contain, every fixed rule gets something wrong:
markR G Bredluminancemaxwanted
cyan guilloche175 215 225inkpaperpaperpaper
black rule35 35 38inkinkinkink
red stamp150 30 35inkinkinkpaper
blue ink signature60 60 200inkinkpaperink
max drops the guilloche but also drops a blue signature, which is content. Luminance keeps the signature but keeps the stamp. Red keeps the guilloche. No column is clean.

So the collapse is a per-document decision, and it belongs beside cut and darken as a control — grey · lightest · darkest · red / green / blue — defaulting to luminance. That is only possible if the crop still carries colour, which is the change above.
And darken alone can never separate a ground The gamma is monotonic: it only moves values down. A ground already darker than cut is pushed further in, never out. Raising cut does not help either — it swallows faint rules first. Neither slider can do this job, which is what justifies a separate step.
Step 2 is the hard part — no single property defines background It is tempting to say background is the coloured, or the lighter, or the ornate thing. None of those generalise. For a tool that must take any document:
guessbreaks on
background is coloureda neutral grey watermark; a black-printed guilloche
background is lightera dark stamp; a faint pencil rule that is content
background is curvy / ornatestraight-line and lattice meshes
background is thinnervaries with scan dpi; a hairline rule is thinner still
Every one of these describes these two documents rather than documents in general.
What actually holds: background is a ground, content is a mark Strip away tone, hue and shape and two properties survive, because they follow from what a background is for:
propertybackgroundcontent
ubiquity — where it occurseverywhere, by design; it is a groundonly where there is something to say
uniformity — how it variesone ink, one pass: near-constant tone and stroke widthvaries freely — rules, text, marks of every weight
Both are measurable without deciding anything about colour. Tile the crop and measure ink coverage per tile:
regiontiles occupiedmeanstd devreading
guilloche mesh16 / 1611.4%0.9a ground
table rules4 / 1610.3%17.9marks
Near-identical mean, utterly different distribution. Any measure that looks only at how much ink there is will confuse these two; one that looks at how it is spread will not.
What is implemented — an opt-in ground removal built A checkbox, off by default, plus a ground ≥ share threshold. When on, it builds a tone histogram of the crop and looks for a ground — a large population at one tone, which is what one ink laid down in one pass produces. Content is a small population spread over many tones.

It searches only BELOW cut. That is the whole correction: a ground lighter than the threshold is already excluded from the mask, so removing it would change nothing. Only a ground dark enough to become ink can do damage, and that is the only band worth touching.

The guilloche sits entirely above cut = 190, so it never enters the mask. On this document the honest answer is to do nothing, and the feature correctly declines.

The first version got this wrong — it treated paper as a single tone, latched onto 254, found its "densest band" at 246 (still paper), and lifted 84% of the page to white while changing the ink count by exactly zero. That is what testing against a real scan caught and a synthetic mesh did not.
Two approaches that were tried and failed do not revisit Both were plausible enough to write down, and both were wrong when measured:
approachwhat actually happened
divide by a local maxthe max over a radius finds the paper between mesh lines, so the estimate is 255 everywhere and the division is a no-op — a mesh at 175 came back 179
divide by a local closingthe closing finds the darkest locally-ubiquitous tone, which is the rule — so rules were divided away and the mesh survived, exactly backwards
threshold max(R,G,B)a no-op: the server renders csGRAY, so all three channels already hold the same value. The idea was sound and the premise was false
The reason is structural, and worth keeping: a mesh line and a rule are locally identical — both are thin dark strokes. They differ only at page scale, in that the mesh line has a parallel partner a few pixels away everywhere while the rule is alone. No local window can separate them, so no local estimate can either. The histogram works precisely because it is a global measure.

The multiplicative reasoning behind division is still correct — ink is multiplicative — but it only helps once you already know which layer is the ground, which is the whole problem.
Fallback — only if the histogram test is not enough It handles anything that behaves like a ground: one ink, one pass, a large share of the crop. A ground printed in several tones, or one covering less of the page than the table's own rules, would defeat it. Then fall back to per-region signals and let them vote, rather than committing to one rule:
signalbackground looks likecost
recurrencemany near-identical regions across the pagehash size+tone, count collisions
coverage spreadpresent in almost every tile, low varianceone tiled histogram
local contrastweak against its own surroundlocal max − min
chromaticityunavailable — pages render greyscale—
Colour is struck from that list entirely: pages arrive greyscale, so there is no hue to test. Recurrence is the signal that survives every case tried, including a black guilloche, where local contrast reads 160 — indistinguishable from a real rule.

The knob users understand is a single "remove background" strength — the radius of the ground estimate — not a threshold on any of these.
Why any of this must precede the mask the downstream cost Background that survives into the binary mask is not merely noise. Stage 4 mends it into the rules it touches, and stage 7 counts its crossings as structure. A mesh covering every cell hands the crossing stage thousands of false partners, and once mended into a rule, nothing downstream can separate them again.

One caveat on the evidence: a mesh that is genuinely denser than the table's own rules will win any vote based on ubiquity — at which point the right move is to treat the dominant repeating pattern as the ground and subtract it, rather than to classify pixel by pixel.

Threshold to binary ink

darkenValue(d[j], g) < cut → 1

Every pixel of the darkened grey below cut (default 190) becomes ink. One bit per pixel: no colour, no greyscale survives.

Consequence Printed rules, text, stamps, pencil marks and a security-print mesh are now identical — all just "ink". Every later stage must separate them by shape alone, with no colour and no grey level to appeal to.
Nothing can be separated here By this line the page is already one channel. The threshold is only the last step of a decision made at stage 2 — which is where the background fix belongs.
carries → scanned (binary mask — colour is gone from here on)

Mend toner voids changed

closeGaps(ink, w, h, mendSpan)

A printed rule reaches the page in pieces, split by holes where the toner did not take. Any blank run with ink on both sides, shorter than the tolerance, is filled — the two axes closed separately, then unioned.

What changed — and why it was wrong Was a fixed 5 px. But stage 1 magnifies a small crop up to 4×, so five raster pixels meant four different physical sizes depending on which table it ran on. A toner void is physical; the number bridging it must scale with the raster.

Now mendSpan = (pct/100) × √(w·h) — the side of the equal-area square. Since w,h are already post-enlargement, this lands on the same physical gap at any magnification. Default 1%.

Merge into lines, then join collinear pieces changed

mergeLines() → joinCollinear()

mergeLines stacks parallel runs: segments in adjacent rows (±1) overlapping by more than 60% of the shorter one are one line. This turns a 7 px-thick rule into a single object rather than seven.

joinCollinear (new) handles the other axis: two pieces of one rule separated along their length. mergeLines cannot do this — its 60% overlap test is about parallel stacking, and two pieces split along their length overlap by zero there, by construction.

Two invariants this must respect 1 · No extension along the length. The run extent is the union of two spans that already exist, so no endpoint moves outward and no free end grows into empty space. A crossing that holds after a join held before it. A line reaching a perpendicular only because it was stretched is not connected, and must not be allowed to look connected.

2 · Straighten, don't bound. On a skewed scan the pieces sit at different heights; the union band is fatter than either. Since crosses() tests that box, a union would widen the line's reach and let it meet perpendiculars neither piece touched. So centre and thickness are averaged, weighted by length — a long piece knows where the rule is, a stub does not.
Second benefit: the lattice stays honest ruleThick (stage 10) is a Math.max over every connected line's band and sets clustering tolerance for the whole table. One skew-fattened join would inflate it globally. An averaged band cannot.
carries → hLines, vLines — rectangles with {x0,y0,x1,y1,len,thick}

Crossing — pure connectivity changed

crosses(a, b) — inclusive AABB overlap

A line is kept when it overlaps at least minCross perpendiculars (default 1).

What changed: the length threshold is gone minPartner = 5% of min(w,h) · vBig · hBig · the cross ≥ slider

Previously a crossing only counted if the partner was long enough — a size judgement standing in for a structural one. Every line is valid; size says nothing about whether it is structure. A short rule between two close columns is as real as the frame. Partners are now the full line sets.

After this change there is no length comparison anywhere in the line stages.
The extension rule, and why it needs no new code If a line already touches another line, it is a boundary. If it would only touch one when extended, the act of extending proves it was not connected. crosses() is plain inclusive overlap with zero tolerance — it never extends anything, so the rule is already honoured. The work was in not breaking it at stage 6.

Spanning — both ends anchored

spanOK(line, partners, horiz, limit)

A real divider runs from one perpendicular across to another. Both endpoints must land inside a different perpendicular's own thickness band. The crop border counts as an anchor, and each border is its own.

Known weakness not solved This assumes a table is a closed lattice. A title block is a ruled form: the MANAGER / CHIEF / CHECKED / DRAWN / DATE underlines end in whitespace, with no printed vertical at the left. Their low end anchors on nothing, so a.length === 0 and the rule dies — despite a perfectly good right-hand anchor.

This is why horizontals collapse 22 → 5. It is the next thing to fix.
Deliberately zero tolerance An earlier version measured to the partner's centre with slack, which broke on thick rules: a 7 px rule spans y130–137, so a vertical starting at y136 is inside it yet 3 px from centre. Measuring against the span makes the question exact.

Connected component

union-find over 90° crossings

Every surviving line is a node; every 90° crossing an edge. Keep only the component the outer border belongs to — the largest by bounding box. Anything floating inside a cell, with no path out to the frame, is not part of the table.

This is where table membership is actually decided Table boundaries are connected. That principle is enforced here, not by per-line size tests upstream — which is exactly why stage 7 can afford to stop filtering by length.
carries → hConn, vConn, frame (its bounding box)
↓
snap onto a lattice, flood the closed regions
11

Lines → cells

buildTable(hConn, vConn, frame, ruleThick)

Rule centres are clustered onto shared xs / ys coordinates, each lattice edge is marked as carrying a wall or not, then each open interior is flooded. A flood cannot step across a rule, so it stops exactly at the cell walls.

Merged cells need no special case A merged cell comes out as one region however many lattice units it covers — nothing has to be told in advance which merges exist. The frame's four sides are added as implicit rules, or the outermost column never closes.
The clustering tolerance is read off the data ruleThick = max(every connected line's band width) — its one job is to merge the two edges of a single thick rule into one lattice coordinate, so the thickest rule actually found is the right tolerance. Stage 6's straightening keeps this number honest.
carries → table — {xs, ys, rows, cols, cells[]}, each cell with rowspan / colspan / rect

Open problems, in the order they bite

what this document says to fix next

stageproblemdirection
0 · upload The page is rendered csGRAY and cached, so colour is destroyed before the user has drawn a single box — the earliest possible moment, with the least evidence. No later stage can recover it. Store the render in colour, let the user mark boxes on the original, and choose the grey collapse after the crop — where a grey · lightest · darkest · R/G/B control can be judged against the actual document. No single collapse is right for every page: max drops a cyan mesh but also a blue signature; luminance keeps the signature but keeps a red stamp too.
2 · darken A ground dark enough to cross cut lands in the mask, and stage 4 then mends it into the rules it touches. (Not the case on the certificate tested — its guilloche sits above cut and never reaches the mask.) Done — opt-in "remove background" checkbox, off by default. Finds the densest tone band below cut and lifts it out; declines when there is none. Five cases verified, including clean-scan and faint-rule no-ops.
8 · spanning Demands both endpoints sit inside a perpendicular. Assumes a closed lattice; a ruled form has rules that end in whitespace. Horizontals collapse 22 → 5. Accept one solid anchor, or anchor on the projected lattice coordinate rather than a physical partner.
Why the order matters Stage 3 comes first not because it is worse but because it is upstream: every later stage reads the mask it produces, and colour — the cheapest way to identify a stamp — is discarded there and unrecoverable afterwards.
